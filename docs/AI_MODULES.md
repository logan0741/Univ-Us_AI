# AI 기능별 MVP 정의

프로젝트 계획서의 17개 기능(F1~F17)을 **9개 AI 기능**으로 재편한 문서입니다.
작업을 시작하기 전에 **자기 기능 항목을 먼저 읽으세요.**

## 이 문서보다 먼저 읽을 것

| 문서 | 무엇이 있나 |
| --- | --- |
| [**기능 명세서**](../Univ-Us_기능명세서.md) | F1~F17 요구사항, 데이터 흐름(DF-1~DF-5), 인수 기준 |
| [**역할별 기능 분해서**](../Univ-Us_역할별_기능분해서.md) | AI/BE/FE 역할 경계, 영역 간 인터페이스 계약 |

이 문서는 위 두 문서를 **"AI 저장소가 어떻게 구현할지"** 로 옮긴 것입니다.
기능 정의가 서로 다르면 **위 두 문서가 기준입니다.**

> 기능 요구사항·데이터 흐름·인수 기준은 위 두 문서에 있습니다.
> 다만 **기술 스택 원칙(4.3), 프로젝트 목표(G1~G4), 협업 규칙(6.2)** 은 두 문서가 범위에서 제외한 항목이라
> 계획서 원본에만 있습니다. 원본은 개인정보가 포함되어 저장소에 두지 않으니 팀 채널에서 받으세요.

브랜치·커밋·이슈 규칙은 [README](../README.md)에 있습니다.

---

## 이 문서를 쓰는 법

각 기능마다 아래 형식으로 정리되어 있습니다.

| 항목 | 뜻 |
| --- | --- |
| **모델 슬롯** | 어떤 종류의 모델이 필요한지. 실제 모델명은 아직 정하지 않았습니다 |
| **MVP 입력 / 출력** | 이 정도가 되면 "1차 완성"이라고 부를 수 있는 최소 범위 |
| **완료 기준** | 전부 체크되면 기능 메인 브랜치로 PR을 올립니다 |
| **MVP 이후** | 1차가 끝난 뒤 이어서 할 일 |

**MVP는 "잘 만든 것"이 아니라 "동작하는 것"입니다.** (계획서 2.2: 완성 기준은 문서상 설계가 아니라 실제로 동작하는 데모)
예외 처리·성능·예쁜 코드는 MVP 다음에 합니다. 먼저 끝까지 한 번 통과시키세요.

## MVP 정의 (한눈에)

| 기능 | 브랜치 | MVP 한 줄 | 모델 슬롯 |
| --- | --- | --- | --- |
| 공통 기반 | `core_ai-agent` | 설정만 바꿔 모델을 갈아끼울 수 있는 LLM 호출 계층 | — |
| 문서 → 일정 | `doc_ai-agent` | 강의계획서 PDF 1건 → 검증된 일정 JSON | `LLM_MAIN` `DOC_PARSER` |

| 아침 브리핑 | `brief_ai-agent` | 오늘 일정 JSON → 브리핑 텍스트, 정해진 시각 자동 실행 | `LLM_MAIN` |
| 대화형 에이전트 | `chat_ai-agent` | 자연어 문장 → 도구 호출 → 자연어 응답 | `LLM_MAIN` |
| 공지 매칭 | `notice_ai-agent` | 공지 원문 → 자격요건 JSON → 해당/비해당 판정 | `LLM_MAIN` `EMBEDDING` |
| 규칙 계산 | `rule_ai-agent` | LLM 없이 순수 함수로 계산, 테스트 전부 통과 | `RULE` |
| 평가 | `eval_ai-agent` | 테스트셋으로 정확도 자동 산출, 모델 비교표 출력 | — |

## 모델 슬롯

계획서 4.3 나 — *"LLM 호출부는 OpenAI 호환 인터페이스로 추상화하여 특정 모델에 종속되지 않는 구조로 설계한다"*

**사용할 모델은 아직 정하지 않았습니다.** 코드에는 모델 이름 대신 슬롯 이름을 씁니다.

| 슬롯 | 역할 | 요구 조건 | 환경변수 |
| --- | --- | --- | --- |
| `LLM_MAIN` | 판단·생성·구조화 추출 | JSON 구조화 출력, Function Calling | `LLM_MAIN_*` |
| `DOC_PARSER` | 문서 레이아웃·표 인식 | PDF·이미지 → 텍스트 + 표 구조 | `DOC_PARSER_*` |
| `VISION` | 이미지 이해 | `pic` 전용. `DOC_PARSER`로 충분하면 안 씀 | `VISION_*` |
| `EMBEDDING` | 청크 벡터화 | 한국어 문서 검색 품질 | `EMBEDDING_*` |
| `RULE` | 결정적 계산 | 모델 아님. 순수 Python | — |

실제 모델은 `eval_ai-agent`의 비교 실험 결과로 정합니다. 정해지면 `.env`와 `requirements.txt`만 바뀝니다.

## 개발 순서

[기능명세서 5.2 구현 순서와 의존 관계](../Univ-Us_기능명세서.md)를 따릅니다.
뒤 기능이 앞 기능의 결과물 위에 올라가므로 순서가 중요합니다.

| 시기 | 기능 | 달성 계층 | 이유 |
| --- | --- | --- | --- |
| 1단계 | `core` → `doc` | 필수 (F1·F6) | 나머지 전부가 이 둘 위에 올라갑니다 |
| 1단계 | `eval` (테스트셋 구축) | — | 정확도를 못 재면 개선했는지 알 수 없습니다 |
| 2단계 | `brief` · `chat` · `rule`(F7 우선순위) | 필수 (F10·F9·F7) | 기반 통합 데모를 만드는 조합 |
| 3단계 | `rule`(나머지) · `notice` · `rag` · `pic` | 목표 (F2·F3·F5·F8·F11~F13·F4) | 병렬 개발 가능 |
| 3단계 | `rule`(F14 시간표 · F16 공강 교집합) | 도전 | 앞 단계가 전부 끝난 뒤 |
| 4단계 | `eval` (모델 비교 실험) | — | 사용 모델 최종 확정 |

**달성 계층**은 기능명세서 5.1의 구분입니다. 계층별 판단 기준이 다릅니다.

| 계층 | 기능 | 이 저장소의 담당 | 판단 기준 |
| --- | --- | --- | --- |
| **필수(Must)** | F1, F6, F7, F9, F10 | `doc` `pic` `rule` `chat` `brief` | 통합 데모에서 오류 없이 동작할 것 |
| **목표(Should)** | F2, F3, F4, F5, F8, F11, F12, F13 | `rule` `rag` `notice` | 동작 + 인수 기준 충족 |
| **도전(Could)** | F14, F15, F16, F17 | `rule` (F14·F16 계산부만) · 나머지는 백엔드 저장소 | 전 기능 통합 및 시범 사용자 운영 |

> `pic`은 F1·F6(필수)의 **이미지 입력 경로**입니다. 텍스트 경로(`doc`)가 먼저 서야 뒷단을 공유할 수 있어 3단계에 둡니다.

# 1. `core_ai-agent` — 공통 기반

> 계획서 4.3 나·라

## 왜 필요한가

모델이 정해지지 않았고, 앞으로 바뀔 수도 있습니다. 8개 기능이 각자 자기 방식으로 API를 호출하면
모델을 바꿀 때 8곳을 전부 고쳐야 합니다. **호출 지점을 한 곳으로 모읍니다.**

토큰 비용 관리(계획서 4.3 라)와 프롬프트 버전 관리도 여기서 합니다.

## 모델 슬롯

없음. 다른 기능이 슬롯을 쓸 수 있게 해주는 계층입니다.

## MVP

| | 내용 |
| --- | --- |
| 입력 | 프롬프트 + 기대하는 Pydantic 스키마 |
| 출력 | 스키마 검증을 통과한 객체 |

## 완료 기준

- [ ] `.env`의 슬롯 설정만 바꿔서 **서로 다른 프로바이더 2개** 로 같은 호출이 성공한다
- [ ] LLM이 스키마에 안 맞는 JSON을 뱉으면 자동 재시도하고, 계속 실패하면 명확한 예외를 던진다
- [ ] 호출마다 **토큰 사용량이 로그에 남는다** (누가 얼마나 쓰는지 봐야 비용 관리가 됩니다)
- [ ] 같은 입력을 다시 넣으면 캐시에서 반환한다 (개발 중 토큰 낭비 방지)
- [ ] 프롬프트가 코드 안 문자열이 아니라 `prompts/` 아래 파일로 있다
- [ ] 다른 기능 담당자가 README만 보고 `core`를 호출할 수 있다

## MVP 이후

- 호출 실패 시 재시도 정책 세분화 (rate limit / timeout / 서버 오류 구분)
- 기능별 토큰 사용량 집계 리포트

## 주의

**이 코드는 8개 기능이 전부 씁니다.** 인터페이스를 바꾸면 다른 사람 코드가 조용히 깨집니다.
공개 함수 시그니처를 바꿀 때는 **반드시 이슈로 먼저 공유**하세요.

# 2. `doc_ai-agent` — 문서 → 일정 추출

> [기능명세서](../Univ-Us_기능명세서.md) 3.1 **F1**(학사일정 자동 등록) · 3.3 **F6**(과제 마감 자동 등록) · 데이터 흐름 **DF-1**

## 왜 필요한가

이 프로젝트의 **핵심 기능**입니다. 계획서 목표 G1이고, [인수 기준(기능명세서 6장)](../Univ-Us_기능명세서.md)의 첫 줄인
"일정 추출 정확도 90% 이상"이 이 기능을 가리킵니다. 여기가 안 되면 나머지 기능이 쓸 데이터가 없습니다.

## 모델 슬롯

`LLM_MAIN` (구조화 추출), `DOC_PARSER` (표가 있는 PDF)

## MVP

| | 내용 |
| --- | --- |
| 입력 | 강의계획서 PDF 1건 (텍스트 기반) |
| 출력 | `{과목, 유형, 제목, 마감일시, 비중, 출처문장}` 리스트 |

`유형`은 `과제` / `시험` / `학사` 중 하나입니다.

## 완료 기준

- [ ] PDF에서 텍스트를 뽑아 `LLM_MAIN`에 스키마를 지정해 JSON을 받는다
- [ ] 결과를 Pydantic 스키마로 검증한다 (형식 오류·필드 누락을 여기서 차단)
- [ ] **날짜 검증**: 존재하지 않는 날짜(2월 30일), 학기 범위 밖 날짜를 걸러낸다
- [ ] **중복 검증**: 같은 과제가 두 번 잡히면 하나로 합친다
- [ ] **모든 항목에 `출처문장`이 붙는다** — 원문 어디서 뽑았는지 없으면 사용자가 검증할 수 없습니다
  (기능명세서 DF-1 필수 조건 · 4장 공통 요구사항 "근거 제시")
- [ ] 확신이 낮은 항목은 자동 등록하지 않고 **"확인 필요" 목록으로 분리**한다 (기능명세서 4장 "저신뢰 분리")
- [ ] 출력 스키마를 `src/schemas/` 에 두고 **`pic_ai-agent`와 공유**한다
  → 역할별 분해서 5장의 `추출 출력 스키마 (AI → BE)` 계약에 해당합니다. 필드·타입·필수 여부·신뢰도 범위를 BE와 먼저 합의하세요
- [ ] 샘플 강의계획서 5건에서 마감일이 수동 검수 결과와 일치한다

## MVP 이후

- 표 형태 강의계획서 → `DOC_PARSER`의 표 인식 결과를 붙여 재시도
- 학사 공지 / 이메일 본문으로 입력 확장
- `eval_ai-agent` 테스트셋(50건)으로 정확도 측정 → 90% 목표
- **F7 예상 소요시간 추정** — 과제 추출 시 선택 필드로 함께 산출해 `rule_ai-agent`에 넘깁니다 ⚠️ 팀 확인 필요
- **F14 강의평 요약** — 시간표 생성(F14)이 쓸 강의평 요약. 텍스트 요약이라 여기가 자연스럽습니다 ⚠️ 팀 확인 필요

> 위 두 항목은 역할별 분해서에서 **AI 보조 역할**로 정의된 작업입니다(F7 `예상 소요시간 추정`, F14 `강의평 요약`).
> `rule_ai-agent`는 LLM을 호출하지 않으므로 **추정은 여기서 하고 값만 넘기는** 구조로 제안합니다.
> 담당 모듈 배정은 아직 팀 합의 전입니다 — 이슈로 확인하세요.

## 주의

- **LMS 자동 로그인 크롤링은 MVP 범위가 아닙니다.** 기능명세서 F6 제약과 2.2 데이터 소스 정의에서
  *"이메일 알림 / 파일 업로드(기본), 자동 로그인 수집(선택)"* 으로 분리돼 있습니다.
  파일 업로드와 이메일 본문을 기본 경로로 잡으세요.
- 날짜 표기가 제각각입니다. `6/12(목) 23:59`, `6월 12일`, `12주차` 같은 형식을 모아두고 하나씩 늘려가세요.

# 3. `pic_ai-agent` — 사진·이미지 분석

> [기능명세서](../Univ-Us_기능명세서.md) 3.1 **F1** · 3.3 **F6** 의 이미지 입력 경로 · 데이터 흐름 **DF-1**

## 왜 필요한가

학생이 실제로 가진 자료는 PDF만이 아닙니다. **시간표 캡처, 강의계획서 사진, 필기 사진**이 훨씬 많습니다.
`doc_ai-agent`가 텍스트를 다룬다면, 여기는 **텍스트가 아닌 입력을 텍스트로 만드는 앞단**입니다.

## 모델 슬롯

`DOC_PARSER` (레이아웃·표 인식), `VISION` (`DOC_PARSER`로 부족할 때만)

> `DOC_PARSER`만으로 충분한지 먼저 확인하세요. 되면 `VISION`은 쓰지 않습니다. 호출이 하나 줄어듭니다.

## MVP

| | 내용 |
| --- | --- |
| 입력 | 시간표 또는 강의계획서를 찍은 사진 1장 (JPG/PNG) |
| 출력 | 텍스트 + 표 구조 JSON (시간표면 `{과목명, 요일, 시작, 종료, 강의실}`) |

## 완료 기준

- [ ] 이미지에서 텍스트와 **표 구조**를 뽑는다 (표를 줄글로 만들면 시간표를 복원할 수 없습니다)
- [ ] 시간표 사진 5장에서 과목명·요일·시간이 나온다
- [ ] 기울어짐·그림자·저해상도 사진에서 **실패를 감지하고 "확인 필요"로 분리**한다
  → 잘못 읽은 결과를 조용히 등록하는 게 못 읽는 것보다 나쁩니다
- [ ] 결과를 `doc_ai-agent`와 **같은 스키마**로 넘긴다 (그래야 뒷단을 공유합니다)
- [ ] 실패한 이미지와 원인을 기록으로 남긴다

## MVP 이후

- 필기 사진 → `rag_ai-agent` 색인 대상으로 연결
- 전처리(기울기 보정·대비 개선)로 인식률 개선
- 로컬 OCR과 API 방식의 정확도·비용 비교 (`eval_ai-agent`와 협업)

## 주의

- 로컬 OCR 모델을 돌리려면 GPU가 필요합니다 → `requirements-gpu.txt`
- **GPU가 없어도 API 경로로 개발할 수 있습니다.** GPU는 비교 실험 단계에서 필요합니다.
- 사진에는 이름·학번이 찍혀 있을 수 있습니다. 이슈에 올릴 때 **가린 뒤 올리세요.**

# 4. `rag_ai-agent` — 강의자료 RAG

> [기능명세서](../Univ-Us_기능명세서.md) 3.2 **F4**(강의자료 요약·시험 예상 문제) · 데이터 흐름 **DF-3** · 계획서 목표 G4

## 왜 필요한가

일정 관리를 넘어 **학습 단계까지** 지원하는 기능입니다(G4). 사용자마다 강의자료가 다르기 때문에
모델이 미리 학습할 수 없고, 검색해서 근거로 삼는 방식(RAG)이 필요합니다.

## 모델 슬롯

`EMBEDDING` (청크 벡터화), `LLM_MAIN` (요약·문제 생성)

## MVP

| | 내용 |
| --- | --- |
| 입력 | 강의 PDF 1개 + 질문 1개 |
| 출력 | 답변 + **출처(파일명·페이지)** |

## 완료 기준

- [ ] PDF를 **페이지·소제목 단위**로 청크 분할하고, 메타데이터에 파일명·페이지를 저장한다
- [ ] `EMBEDDING`으로 벡터화해 pgvector에 저장한다
- [ ] 질문을 넣으면 코사인 유사도 top-k 청크를 가져온다
- [ ] **답변에 출처 페이지가 100% 표기된다** — [인수 기준(기능명세서 6장)](../Univ-Us_기능명세서.md)의
  "자료 응답 근거성 95% 이상"이 이 항목을 잽니다. 기준이 95%인데 100%를 목표로 두는 이유는, 구현이 100%를 노려야 실측이 95%를 넘기 때문입니다
- [ ] 검색된 청크에 없는 내용은 답하지 않는다 (모르면 "자료에 없다"고 답한다)
- [ ] 같은 자료로 시험 예상 문제 3개를 생성한다

## MVP 이후

- 하이브리드 검색 (벡터 + 키워드) — 계획서 4.4 마
- 청크 크기·top-k 값을 바꿔가며 검색 품질 비교
- 출처 표기율 표본 검사 자동화
- **F5 강의자료 분량·난이도 추정** — 이미 자료를 청킹하므로 분량 산출이 자연스럽습니다.
  결과는 `rule_ai-agent`의 시험 공부 일정 역산(F5)에 **입력값으로** 넘깁니다 ⚠️ 팀 확인 필요

## 주의

**출처 표기가 이 기능의 존재 이유입니다.** 근거 없이 그럴듯한 답을 만드는 건 이 기능이 막으려던 문제 그 자체입니다.
답변만 잘 나오고 출처가 비면 MVP 미완성으로 봅니다.

# 5. `brief_ai-agent` — 아침 브리핑

> [기능명세서](../Univ-Us_기능명세서.md) 3.3 **F10**(아침 브리핑) · 데이터 흐름 **DF-2** · 계획서 목표 G2

## 왜 필요한가

[기능명세서 1.3 제품 원칙](../Univ-Us_기능명세서.md)의 첫 줄이 **능동성(Proactiveness)** 입니다 —
*"학생이 찾아 나서지 않고, 시스템이 필요한 시점에 먼저 알린다."*
사용자가 찾아오는 게 아니라 **먼저 알려주는** 부분을 실제로 담당하는 기능입니다.

## 모델 슬롯

`LLM_MAIN`

## MVP

| | 내용 |
| --- | --- |
| 입력 | 오늘 일정 + 마감 임박 항목 + 우선순위 점수 JSON |
| 출력 | 브리핑 텍스트 |

## 완료 기준

- [ ] **고정된 입력 JSON**으로 브리핑을 생성한다 (DB 연동 전에 파일 입력으로 먼저 만드세요)
  → 이 JSON 구조가 역할별 분해서 5장의 `브리핑 입력 (BE → AI)` 계약이 됩니다. 형태를 정하면 BE에 공유하세요
- [ ] 마감 임박 기준을 **D-3 이내**로 잡아 우선 노출한다 (기능명세서 3.3 F10 · DF-2)
- [ ] APScheduler로 정해진 시각에 1회 자동 실행된다
- [ ] 실행 실패 시 재시도하고 로그를 남긴다
- [ ] 일정이 하나도 없는 날에도 자연스러운 문장이 나온다 (빈 목록 처리)

## MVP 이후

- `rule_ai-agent`의 우선순위 점수(F7), 학습 블록(F8)을 브리핑에 반영
- 알림 채널 연동 (웹 푸시 / 이메일)
- 브리핑 품질 만족도 평가 (5점 척도, 목표 4.0 이상)

## 주의

**알림 피로(notification fatigue)** — 기능명세서 1.3 제품 원칙 "선별 알림"과 4장 공통 요구사항 "알림 정책"에 명시된 설계 원칙입니다.
"모든 정보를 알리는" 게 아니라 **"지금 필요한 것만 골라 알리는"** 방향입니다.
브리핑이 길어지면 아무도 안 읽습니다. **짧게 만드는 게 기능입니다.**

# 6. `chat_ai-agent` — 대화형 에이전트

> [기능명세서](../Univ-Us_기능명세서.md) 3.3 **F9**(자연어 일정 등록·질의) · 데이터 흐름 **DF-4**

## 왜 필요한가

*"다음 주 목요일 발표 리허설 저녁 8시에 넣어줘"*, *"이번 주 마감 뭐 남았어?"* 를 처리합니다.
Function Calling으로 **모델이 도구를 골라 실행하고, 결과를 다시 자연어로** 돌려주는 구조입니다.

## 모델 슬롯

`LLM_MAIN` (Function Calling 지원 필수)

## MVP

| | 내용 |
| --- | --- |
| 입력 | 자연어 문장 1개 |
| 출력 | 도구 실행 결과 + 자연어 응답 |

## 완료 기준

- [ ] 도구 3개를 정의하고 등록한다 — `일정 등록` / `마감 조회` / `우선순위 조회`
  → 역할별 분해서 5장의 `도구 목록 (BE → AI)` 계약입니다. **함수 이름·파라미터·읽기/쓰기 구분을 BE와 먼저 확정**하세요
- [ ] 문장을 넣으면 **맞는 도구가 선택되고 인자가 채워진다**
- [ ] 도구 실행 결과를 모델에 다시 넣어 자연어로 답한다
- [ ] **쓰기 작업(일정 등록·수정)은 실행 전에 사용자 확인을 거친다**
- [ ] 어느 도구에도 해당하지 않는 문장에는 "할 수 없다"고 답한다 (억지로 도구를 부르지 않는다)
- [ ] 상대 날짜를 해석한다 — "다음 주 목요일", "내일", "이번 주"

## MVP 이후

- 도구를 F2(졸업요건 조회), F4(자료 질의)까지 확장
- 대화 이력 유지 (여러 턴에 걸친 일정 수정)
- 응답 스트리밍

## 주의

**쓰기 작업에는 반드시 확인 단계를 넣으세요.** 기능명세서 1.3 제품 원칙 "신뢰 우선", 4장 공통 요구사항 "승인 흐름",
그리고 DF-4의 *"쓰기(등록·수정·삭제) → 실행 전 사용자 확인 [필수]"* 에 해당하는 Human-in-the-loop 원칙입니다.
모델이 잘못 알아듣고 남의 캘린더에 일정을 넣거나 지우면, 그 시점에 신뢰가 끝납니다.

# 7. `notice_ai-agent` — 공지 수집·매칭

> [기능명세서](../Univ-Us_기능명세서.md) 3.4 **F11**(장학) · 3.5 **F12**(대외활동)·**F13**(사업단 공지) · 데이터 흐름 **DF-5**

## 왜 필요한가

장학금·공모전은 **몰라서 놓치는** 경우가 대부분입니다.
공지를 모아서 자격 요건을 뽑고, 사용자 프로필과 맞는 것만 골라 알립니다.

## 모델 슬롯

`LLM_MAIN` (자격 요건 구조화 추출), `EMBEDDING` (관심사 유사도 매칭)

## MVP

| | 내용 |
| --- | --- |
| 입력 | 공지 원문 10건 + 사용자 프로필 |
| 출력 | 자격요건 JSON + 해당/비해당 판정 |

프로필 예시: `{학년, 이수학점, 전공, 성적, 관심사}`

## 완료 기준

- [ ] 공지 본문에서 자격 요건을 구조화해 뽑는다 (`최소학점`, `학년제한`, `전공제한`, `신청마감일`)
- [ ] **매칭 판정은 LLM이 아니라 규칙 코드로 한다**
  → "18학점 이상"은 계산의 영역입니다. 모델에게 맡기면 틀립니다
- [ ] 프로필 3종(해당 / 비해당 / 애매)으로 판정 결과를 확인한다
- [ ] 판정 근거를 남긴다 — "3학년 이상 조건 미충족" 처럼
- [ ] 애매한 경우 자동 제외하지 않고 **"확인 필요"로 분리**한다
- [ ] 공지 10건 판정 결과를 수동 검수해 오매칭 사례를 기록한다
  (인수 기준 "공지 매칭 정밀도 — 오매칭률 10% 이하". 자동 집계는 `eval_ai-agent`가 맡습니다)

## MVP 이후

- 게시판 주기 수집 스케줄러 (APScheduler)
- 신규 공지만 골라내는 중복 판정
- F11 장학금 신청서 초안 자동 작성 → **제출은 반드시 사용자 승인 후**

## 주의

- **놓치는 것(false negative)이 잘못 알리는 것보다 나쁩니다.** 애매하면 버리지 말고 "확인 필요"로 보냅니다.
- 게시판을 수집할 때는 요청 간격을 두세요. 학교 서버에 부담을 주면 안 됩니다.

# 8. `rule_ai-agent` — 규칙 기반 계산

> [기능명세서](../Univ-Us_기능명세서.md) 3.1 **F2**(졸업요건) · 3.2 **F3**(출결경고)·**F5**(시험공부일정) ·
> 3.3 **F7**(우선순위)·**F8**(학습블록) · 3.6 **F14**(시간표) · 3.7 **F16**(팀플조율 — 공강 교집합 계산만)

## 왜 필요한가

[역할별 분해서 1장](../Univ-Us_역할별_기능분해서.md)의 핵심 경계 원칙 1 — **"판단과 계산을 섞지 않는다."**

졸업까지 남은 학점이 몇 학점인지, 결석을 몇 번 더 할 수 있는지는 **틀리면 안 되는 계산**입니다.
기능명세서 F2에도 *"결정적 계산 — 추론 기반 처리 금지"*, *"계산 결과의 정확성이 100% 보장되어야 함"* 이라고 명시돼 있습니다.

## 왜 AI 저장소에 있나

역할별 분해서 기준으로 보면 결정적 계산은 **BE 영역**입니다. 두 문서를 나란히 읽으면 반드시 헷갈리는 지점이라 먼저 정리합니다.

| 축 | 구분 방식 | `rule` 의 위치 |
| --- | --- | --- |
| **직군** (역할별 분해서) | AI / BE / FE | BE 영역의 계산 |
| **저장소·브랜치** (이 문서) | 9개 AI 기능 | AI 저장소가 구현 |

모순이 아니라 **축이 다릅니다.** AI 저장소가 구현하는 이유는 두 가지입니다.

1. 입력 스키마를 `doc`·`pic` 의 추출 결과와 `src/schemas/` 에서 **공유**합니다
2. 순수 함수라 **테스트가 이 저장소 안에서 닫힙니다** (DB·네트워크가 필요 없음)

**호출은 백엔드가 합니다.** 이 저장소는 호출 가능한 함수와 스키마까지 책임집니다.

## 모델 슬롯

`RULE` — **모델을 쓰지 않습니다. 순수 Python입니다.**

## MVP

| | 내용 |
| --- | --- |
| 입력 | 이수내역 / 시간표 / 과제 목록 |
| 출력 | 계산 결과 (남은 요건, 결석 여유, 우선순위 점수, 학습 블록) |

### 추정값은 만들지 말고 입력으로 받으세요

역할별 분해서는 F5·F7·F14 에 **AI 보조 역할**을 두고 있습니다. 그 값들은 여기서 만들지 않습니다.

| 기능 | 추정이 필요한 값 | 누가 채우나 |
| --- | --- | --- |
| F7 우선순위 | 예상 소요시간 | 사용자 입력 우선 → 없으면 `doc_ai-agent` 가 추정 |
| F5 시험공부일정 | 강의자료 분량·난이도 | `rag_ai-agent` 가 추정 |
| F14 시간표 | 강의평 요약 | `doc_ai-agent` 가 요약 |

**`rule` 은 이 값을 받아서 계산에만 씁니다.** 그래야 *같은 입력 → 같은 출력*이 유지되고 경계값 테스트가 성립합니다.
값이 비어 있으면 기본값으로 계산하거나 "추정값 없음"을 근거에 남기세요.

> ⚠️ 위 담당 모듈 배정은 **아직 팀 합의 전**입니다. 착수 전에 이슈로 확인하세요.

## 완료 기준

- [ ] **LLM을 한 번도 호출하지 않는다** (추정값은 위 표대로 다른 모듈에서 받습니다)
- [ ] 전부 순수 함수로 구현한다 (같은 입력 → 항상 같은 출력)
- [ ] `pytest` 케이스가 전부 통과한다 — **여기는 테스트가 필수입니다**
- [ ] 경계값 테스트가 있다 (결석 한도 딱 도달, 학점 딱 충족, 마감 당일)
- [ ] F7 우선순위 점수식이 **문서로 설명되어 있다** (마감일 + 성적 비중 + 예상 소요시간)
- [ ] 계산 근거를 함께 반환한다 — "전공 6학점 부족" 처럼

### 구현 순서

| 순서 | 기능 | 내용 |
| --- | --- | --- |
| 1 | F7 우선순위 | 브리핑(F10)이 바로 씁니다. 먼저 만드세요 |
| 2 | F3 출결 경고 | 결석 한도(예: 1/4 규정) 추적 |
| 3 | F2 졸업요건 | 남은 전공·교양 학점 계산 |
| 4 | F8 학습 블록 | 공강 시간에 과제 배치 |
| 5 | F5 시험 공부 일정 | 시험일에서 역산 |
| 6 | F14 시간표 · F16 공강 교집합 | 제약 조건 탐색. **F16은 교집합 계산 함수까지만** — 팀 생성·회의 일정 생성·역할 추적은 백엔드 저장소 |

## MVP 이후

- 학과별로 다른 졸업요건을 설정 파일로 분리
- 우선순위 점수식 가중치 조정 (사용자 피드백 반영)

## 주의

**여기서 LLM을 쓰고 싶어지면 잘못 가고 있는 것입니다.** 계산에 애매함이 있다면 규칙이 덜 정의된 것이지
모델이 필요한 게 아닙니다. 애매한 부분은 이슈로 올려 규칙을 먼저 확정하세요.

# 9. `eval_ai-agent` — 평가·모델 비교

> [기능명세서 6장 인수 기준](../Univ-Us_기능명세서.md) · 계획서 4.6 평가 방법

## 왜 필요한가

**정확도를 못 재면 개선했는지 알 수 없습니다.** 프롬프트를 바꿨을 때 좋아진 건지 나빠진 건지
감으로 판단하게 됩니다. 계획서 4.3 라에도 *"테스트셋 정확도가 개선된 경우에만 반영한다"* 고 되어 있습니다.

그리고 **어떤 모델을 쓸지 정하는 것도 이 기능의 몫입니다.**

## 모델 슬롯

없음. 다른 기능의 결과를 채점합니다.

## MVP

| | 내용 |
| --- | --- |
| 입력 | 라벨링된 테스트셋 (문서 + 정답 일정) |
| 출력 | 지표 리포트 (정확도 / 응답시간 / 모델 비교표) |

## 완료 기준

- [ ] 테스트셋 **50건 이상**을 수작업 라벨링해 적재한다 (인수 기준 "테스트셋 50건 이상")
- [ ] 마감일·과제명 기준 **추출 정확도를 자동으로 계산**한다
- [ ] 응답 시간을 측정한다 (목표: 대화 응답 5초 이내)
- [ ] RAG 근거 표기율을 측정한다 (목표: 95% 이상)
- [ ] 명령 한 번으로 전체 평가가 돌고 결과가 파일로 나온다
- [ ] **모델 2종 이상**을 같은 테스트셋으로 돌려 정확도·비용 비교표를 출력한다

### 인수 기준 6개가 어디서 측정되는가

[기능명세서 6장](../Univ-Us_기능명세서.md)의 인수 기준은 **전부 이 기능이 잽니다.** 하나라도 측정 수단이 없으면 그 기준은 달성 여부를 말할 수 없습니다.

| 인수 기준 | 목표 | 측정 대상 | 시기 |
| --- | --- | --- | --- |
| 일정 추출 정확도 | 마감일 기준 90% 이상 | `doc` `pic` | MVP |
| 자료 응답 근거성 | 출처 표기율 95% 이상 | `rag` | MVP |
| 응답 시간 | 대화 응답 5초 이내 | `chat` | MVP |
| 공지 매칭 정밀도 | 오매칭률 10% 이하 | `notice` | MVP 이후 |
| 브리핑 품질 | 5점 척도 평균 4.0 이상 | `brief` | MVP 이후 (사람 평가) |
| 사용성 검증 | 시범 사용자 5인 이상 2주 | 전체 통합 | MVP 이후 (사람 평가) |

> 마지막 두 항목은 **자동 계산이 불가능합니다.** 설문·기록 양식을 미리 만들어 두는 것까지가 이 기능의 몫입니다.

## MVP 이후

- 프롬프트 버전별 정확도 추이 기록 (어떤 프롬프트가 몇 점이었는지)
- **공지 매칭 오매칭률 자동 집계** — `notice`의 수동 검수를 자동화
- **브리핑 만족도 수집 양식** — 5점 척도, 목표 평균 4.0 이상
- **시범 사용자 운영 기록 양식** — 5인 이상 2주 사용 후 개선 항목 도출
- 비교 실험 결과를 정리해 **사용 모델 최종 확정** → `.env` · `requirements.txt` 갱신

## 주의

- **테스트셋 라벨링이 이 기능에서 가장 오래 걸립니다.** 미루면 다른 기능의 정확도를 끝까지 못 잽니다.
  1단계에서 먼저 시작하세요.

## 영역 간 인터페이스 계약

[역할별 분해서 5장](../Univ-Us_역할별_기능분해서.md)이 계약 6개를 정의하고,
*"병렬 개발이 가능하려면 아래 계약이 **기능 착수 전에** 확정되어야 한다"* 고 못박고 있습니다.

그중 **이 저장소가 당사자인 것이 4개**입니다. 코드를 짜기 전에 상대 저장소와 합의하세요.

| 계약 | 방향 | 이 저장소에서 만드는 곳 | 확정 시기 |
| --- | --- | --- | --- |
| 추출 출력 스키마 | AI → BE | `src/schemas/` — `doc`·`pic` 공용 | `doc` 착수 전 |
| 도구 목록 | BE → AI | `chat_ai-agent` 도구 3개 | `chat` 착수 전 |
| 브리핑 입력 | BE → AI | `brief_ai-agent` 고정 입력 JSON | `brief` 착수 전 |
| 검증 실패 규약 | BE → FE | `doc` 의 "확인 필요" 분리 기준이 여기 물림 | `doc` 착수 전 |

나머지 2개(`승인 대기 객체`, `알림 페이로드`)는 BE↔FE 계약이라 이 저장소가 직접 만들지는 않습니다.
다만 **`doc` 의 신뢰도 값**과 **`notice` 의 판정 근거**가 그 화면에 그대로 실리므로, 형태를 바꿀 때는 공유하세요.

> 계약이 늦어지면 병렬 개발이 막힙니다. 확정 전이라도 **임시 형태를 정해 이슈에 올려두고** 시작하세요.
> 나중에 바뀌는 것보다 아무도 시작 못 하는 게 더 비쌉니다.

## 기능 간 공통 규칙

계획서 4.3 라의 품질 관리 원칙, 그리고 [기능명세서 4장 공통(횡단) 요구사항](../Univ-Us_기능명세서.md)을 모든 기능이 지킵니다.

| 원칙 | 하는 일 |
| --- | --- |
| **근거를 함께 반환한다** | 추출 결과에 출처 문장, RAG 답변에 출처 페이지 |
| **확신 없으면 자동 처리하지 않는다** | "확인 필요" 목록으로 분리하고 사용자에게 넘김 |
| **쓰기 작업은 사용자 확인 후** | 캘린더 등록, 신청서 제출 (Human-in-the-loop) |
| **프롬프트는 파일로 버전 관리** | `prompts/` 아래. 정확도가 좋아졌을 때만 반영 |
| **개인 식별 정보는 프롬프트에 넣지 않는다** | 필요하면 항목 단위로 최소화 (계획서 4.4 자 · 기능명세서 4장 "개인정보") |
| **토큰 사용량을 로깅한다** | 반복 호출 구간은 캐싱 |
